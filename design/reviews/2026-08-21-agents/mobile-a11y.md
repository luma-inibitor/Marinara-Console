# UI/UX Review — Memory tool: Mobile ergonomics, keyboard/focus a11y, design-system compliance

> **Status: audited 2026-08-22.** This is the report as it was written on
> 2026-08-21, and its findings haven't been edited. The codebase has moved
> substantially since — the P0 batch shipped and a shared `src/ui/` component
> layer was extracted — so the line numbers cited below no longer resolve and
> some findings describe surfaces that have since been rebuilt. Every finding
> at **[critical]** or **[high]** severity now carries an inline status marker
> (`SHIPPED`, `OPEN`, `SUPERSEDED` or `UNVERIFIED`) naming the evidence.
> Findings without a marker weren't audited: check them against the current
> code before acting on them. The reason this header exists is that the next
> reader, human or agent, will otherwise re-fix a bug that's already fixed, or
> "restore" a bug while reverting what looks like drift.

Tested live at 390x844 (isMobile+hasTouch), 768x1024, 1280x800 against `http://127.0.0.1:7875/#/memory/*`. Sources: `src/tools/memory/*.tsx`, `src/styles/memory.css`, `lorebooks.css`, `base.css`, `tokens.css`, `shell.css`.

## Findings

- **[critical] [mobile]** — The claim detail is unreachable by touch. Tapping a row only sets the cursor: `focusRow` in `Review.tsx` does `if (desktop) detailKey.value = key`, and the only paths that set `detailKey` otherwise are Enter/o/e in the list keydown handler. Measured: tap on `.mem-mid` → `stackOpen: false`, `rowFocused: true`; the stacked detail opened only after a hardware-keyboard Enter. Everything in `ClaimDetail` — text editing, diffs, conflicts, evidence, restates/dupe context, deciding from detail — is dead weight on phone *and* touch tablet (768px shows the same single-pane layout). Fix: in `focusRow`, set `detailKey` on mobile too (tap = open stacked screen; the tri rail already covers tap-to-decide). **[SHIPPED — the roving-focus `onFocus` callback sets `detailKey.value = key` unconditionally and `ClaimRow`'s tap handler goes through it; verified by tapping `.mem-mid` at 486x1085, which opens `.stack-screen` (`Review.tsx`).]**

- **[high] [mobile]** — Hardware/browser back exits the app instead of closing overlays. With the stacked detail open, `history.length` stayed at 2 and back navigated to `about:blank`. Stacked detail, facet sheet, and note peek push no history state (all are signals: `detailKey`, `facetSheetOpen`, `peeked`). On Android this is data-loss-feel: mid-triage back-swipe leaves the console entirely. Fix: `pushState` on overlay open, close on `popstate`. **[SHIPPED — `src/shell/overlays.ts` pushes a history entry per overlay and closes down to the depth `popstate` reports; measured `history.length` 2 → 3 on opening the stacked detail, and browser back closed the facet sheet while staying on `#/memory/review`.]**

- **[high] [a11y]** — The Escape contract (DESIGN §3) breaks whenever focus is inside the thing to close, because the only keydown handler sits on `.audit-list`. Measured: Esc with focus on a decide button inside the stacked detail → stays open; Esc with focus on a facet row inside the sheet → stays open; both close only with focus back on the list. The note peek **never** closes on Esc (mobile or desktop, any focus — `NotePeek.tsx` has no key handling and `onListKey` doesn't know about it). BACKLOG's "Esc dismisses the sheet (done)" only holds while focus never entered the sheet. Fix: document-level Escape dispatch over an overlay stack. **[SHIPPED — the Escape handler is a capture-phase document listener in `src/shell/overlays.ts` that calls `history.back()`, and every layered surface including `NotePeek` now goes through `<Sheet>`, which registers itself; verified Escape from a button inside the stacked detail and from a control inside the facet sheet.]**

- **[high] [design-compliance]** — Density: **4 rows fully visible (5 partial) at 390x844** vs the ~10+/~11 target (DESIGN §2/§7). Breakdown: sticky chrome = mem-nav 45px + console 120.8px + bottom rail 53px (219px, 26% of screen); rows 57–114px; and — the real killer — per-group scaffolding of grouphead 46px + "Keep group / Drop group" action row 50px = **96px per group, with 8 of 12 groups holding a single row** (scaffold-to-content ratio >1 for singles). The Vault renders 10 rows on the identical screen, so the audit-row itself is fine. Fix: suppress `group-actions` for single-row groups (the tri does the same job) or fold bulk actions into the grouphead. **[SHIPPED — the per-group action row is gone (bulk keep/drop are icon buttons in the group head) and rows measure 41px; re-measured at 390x844 on the current corpus: 8 rows fully visible, 9 partial, 0 `.group-actions` in the list. That's short of the ~10 target but the scaffolding this finding named no longer exists (`Review.tsx` `GroupBlock`, `src/ui/ListGroup.tsx`).]**

- **[high] [a11y]** — No roving tabindex anywhere in the review list: 73 tabbable elements inside `.audit-list` (17 rows x 2 buttons + header chips + group actions), so ~74 Tab presses to cross the list and reach the apply dock. DESIGN §3 mandates one tab stop per composite. Note j/k *does* work with focus on any control inside the list (handler bubbles — verified from a header chip), so the roving pattern only needs `tabindex=-1` on non-cursor row controls plus a focus-follow. **[OPEN — `useRovingFocus` moves the cursor and calls `focus()`, but nothing sets `tabindex=-1` on non-cursor row controls; measured 279 tabbable elements inside `.audit-list` at 390x844 and 486x1085, 3 per row. The lorebook audit does set `tabIndex={props.isFocused ? 0 : -1}` per row, so the pattern exists in the repo and the queue hasn't adopted it.]**

- **[medium] [mobile]** — The apply dock obscures the bottom tool nav completely: at 390px the dock (fixed, z-40, measured 102px, spanning y 742–844) covers the rail (top 791). While any decision exists you can't switch to Lorebooks/Presets. At ≥900px the dock starts at `left: 64px` but the rail is **84px** wide — a measured 20px overlap onto the rail (`memory.css` `.apply-dock { left: 64px }` vs `shell.css` grid `84px`). List content itself is safe: last row scrolls clear (padding-bottom 132px > dock 102px) — though a dock with warnings + restore link (3 info lines) will eat most of that 30px margin.

- **[medium] [usability]** — Sticky group headers vanish under the sticky console: after scrolling, a grouphead pins at y 45–91 while the console occupies 45–165.8 at higher z (grouphead `top: 0; z-index: 5` vs console `z-index: 20`, `lorebooks.css`). The "which memory am I deciding on" context — the thing sticky headers exist for — is invisible mid-scroll on all three viewports. Fix: offset `top` by console height (CSS var), or un-stick.

- **[medium] [a11y]** — Focus ring invisible on the active nav rail item: `.rail-item.is-active` sets `box-shadow: inset 0 0 0 1px var(--accent)` (specificity 0,2,0), silently overriding the `:focus-visible` ring (0,1,0). Measured: focused active item shows only the 1px inset — identical to its unfocused state. Every other sampled control shows the proper 2px+4px ring.

- **[medium] [mobile]** — Undo is touch-unreachable exactly when it's most wanted: the dock (the only touch Undo) renders only while `keep+drop > 0` (`ApplyDock` early-return). "Reset shown" or undeciding the last row empties the tally, the dock unmounts with `canUndo` still true, and the only remaining path is the `u` key. Undo-over-confirm (DESIGN §2) needs a touch path that survives the tally hitting zero — for example, an undo toast on bulk reset.

- **[medium] [design-compliance]** — No `?` shortcut cheat sheet exists (grepped shell + tool; DESIGN §3 mandates it). On mobile that's moot, but on desktop the entire a/d/x/space/u vocabulary is taught only by the empty-detail-pane hint, which disappears once a claim is open. (Cmd-K palette exists with proper `aria-modal`; its missing memory entries are already in BACKLOG — the missing `?` sheet isn't.)

- **[medium] [mobile]** — Facet sheet: header (Clear + x) is `position: static` inside the scrolling sheet — content is 980px in a 657px sheet (26 facet rows), and at scroll bottom Clear sits at y −122 (offscreen). Clear *is* visible on open without scrolling (BACKLOG item verified ✓), but after browsing the long tail, clearing/dismissing needs a scroll-back or discovering the 186px scrim strip. Make `.peek-head` sticky within the sheet.

- **[medium] [design-compliance]** — Worst offenders among the known "279 soft tap-target warnings" (the ones that actually matter): (1) **facet rows — 34px min-height with 0px gap, 26 stacked adjacent** — DESIGN's secondary floor requires ≥8px spacing, this is the largest violation cluster; (2) **the chip rail gap is 4px, not the mandated ≥8px** (`.chiprail { gap: 4px }`); (3) **stacked-detail/vault back buttons ‹ at 38x38 without `.hit`** — a primary navigation control on a stacked screen, should be ≥44px; (4) export ⭳ 38x38 without `.hit`; (5) `.notelink` inline note refs at ~32px height, 12px mono. Not a problem: the tri rail (40x24 + `.hit` → effective 44x44) and the peek x (38px + `.hit` → 44).

- **[low] [mobile]** — Chip rail discoverability: 1259px of chips in a 366px viewport (3.4 screens), scrollbar suppressed, no edge fade (the row metaline has a fade mask; the chiprail doesn't). Group-by and sort live 1–2 screens off-canvas; only the accidentally-clipped "Conflicts" chip hints there's more. Same pattern on `mem-nav`: the status line ("23 memories · 4 sources · index healthy") is entirely off-canvas at 390 with no indicator.

- **[low] [mobile]** — The export glyph ⭳ renders as tofu (missing-glyph box) at 390 — the loaded faces lack U+2B73, so the only backup-export affordance is a meaningless box (aria-label is present, sighted users get nothing). Use an SVG or a covered glyph.

- **[low] [design-compliance]** — Engine identifiers set in the prose face: facet values `create_note`, `append_section`, `add_link`, `timeline_event` render in Source Sans via `.fv.t-prose` (verified computed font). DESIGN §1: keys/IDs are data face, ligatures off. (Everything else spot-checked clean: claim text prose, metaline mono, status line mono, tally tabular.)

- **[low] [design-compliance]** — `data-density="compact"` works mechanically but buys nothing here: row height 113.6 → 105.6px, still exactly 4 rows fully visible. Row height is dominated by the 4-line clamp and wrapped metaline, and compact doesn't touch the grouphead/group-actions overhead that actually costs the screen.

- **[low] [a11y]** — Tab badge concatenates into the accessible name: the review tab announces as "Review Queue2" (badge `<b>2</b>` inside the button with no sr-only context). Screen-reader users hear a mystery number; give the badge an `aria-label` ("2 pending drafts") or `aria-hidden` + label on the button. Dialog semantics are also incomplete: sheet/peek have `role=dialog` but no `aria-modal`, focus is never moved in (measured `focusIn: false`) nor returned to trigger; `.stack-screen` has no role at all.

- **[low] [usability]** — While preflight is in flight the dock contradicts itself: primary reads "Apply decided (0)" (disabled) while the info line says "1 draft will be sent". No in-flight indication distinguishes "0 ready" from "still checking".

## What passed (measured)

Reduced motion fully honored (emulated → all `transitionDuration: 0s`, global kill in `base.css`). Focus rings strong (2px canvas + 4px accent) on every sampled control except the active rail item. Zero console/page errors on all screens visited. Tri rail: no accidental-tap risk — effective 44x44, only 2px lateral overlap into the row-open target, and its vertical `.hit` overflow lands in dead rail space. All icon-only buttons have aria-labels; tri label announces current state + action; chips carry `aria-pressed` (16 toggles); tabs use `aria-current="page"`. Scrim tap dismisses sheet and peek. Desktop keyboard loop (j/k, a/d with autoadvance, x, space, Enter, u) works, including with focus on non-row controls. Vault: 10 rows/screen, tap-opens editor, permanent delete confirm()-guarded. Sources selection circles labeled per-row ("Select {title}").

## Count summary

**18 findings: 1 critical, 4 high, 7 medium, 6 low.** By category: mobile 8, a11y 5, design-compliance 6, usability 2 (primary category). The three structural fixes with the highest leverage: set `detailKey` on mobile tap (unlocks the entire detail surface), move Escape/back handling to a document-level overlay stack with history integration, and suppress single-row group scaffolding (roughly doubles visible rows toward the ~10 target).
